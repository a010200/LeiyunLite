# 版本与发布规则

从 v1.2.0 起执行以下规则。以前的 R3/R4/R5、v1.1.0 等历史名称不追溯修改。

## 版本递增

- 每完成维护者提出的一轮软件修复任务，版本号第三位加1，不论是否上传 GitHub。一轮可以包含一个或多个问题。
- 当前版本 v1.2.9：OpenRazer 能力扩展、Viper V4 Pro / Naga V3 Pro 补充协议、发布前纠正层及最大化工作区修复。维护者已授权正式发布；本轮审计和返工仍为 1.2.9 / 1.2.9.0，不重复升号。v1.2.8 标签、附件和历史证据保持。下一新修复轮完成为 v1.2.10；Motion 历史未完成项继续单列。
- 同轮修改、测试、返工只计一次；只做解释、评审、文档更新或上传既有版本，不额外增加软件版本。
- 未经维护者明确要求，不增加第一、第二位。已发布标签和附件不覆盖；新修复使用新版本。
- 程序集、界面、更新比较、构建输出、说明文档与软件包使用同一当前版本。历史说明及测试历史样本保留原编号。

## 每次上传

上传当时已完成的版本源码，并建立对应 `vX.Y.Z` 标签与 Release。每次都提供：

| 文件 | 用途 |
|---|---|
| `LeiyunLite-vX.Y.Z-Setup-x64.exe` | 安装程序 |
| `LeiyunLite-vX.Y.Z-win-x64.zip` | 解压即用便携版，包含主程序、许可证与说明 |
| `LeiyunLite-vX.Y.Z-update-x64.zip` | 安装版的签名更新载荷，不供直接解压运行 |
| `LeiyunLite-vX.Y.Z-update.json` | 项目私钥签名的更新清单，包含版本、文件名单和哈希 |
| `SHA256SUMS.txt` | 上述附件的完整性校验 |

先创建草稿 Release，核对附件大小、SHA256 与源码版本，再公开发布；最后匿名下载复核，确认更新器能够识别。仅创建 Git 标签或上传安装程序不足以启用签名更新。

## 用户更新说明规范

- 用户可见版本说明控制在1～4条，每条只写一个用户能够理解的变化。
- 不写源文件名、测试数量、协议字段或重复安全声明。
- 没有明显用户可感知变化时，使用“修复了一些已知问题，提升软件稳定性。”
- 详细技术记录继续写在CHANGELOG.md、docs/RELEASE-vX.X.X.md和test-artifacts/中。
- UI仅提取简短Markdown条目，原始GitHub Release正文保留，不作为可执行内容或HTML渲染。

## 保存与安全

每轮定版保留独立完整源码快照、安装版、便携版及测试/哈希记录，不覆盖旧版。完整本地快照可能包含本机编辑器路径，不能直接当公开源码上传。

私钥只在仓库外保存，不进入源码、Git 历史、Release、软件包或截图；软件只嵌入公钥。发布只上传经过检查的源文件和上述分发附件，不上传测试程序、编译器、日志、用户宏/设置或凭据。

自动更新只接受更高版本、匹配协议与配置格式且签名正确的稳定版本。便携版不会自动执行下载的程序；v1.1.0 等旧便携版须手动运行一次新安装程序。项目更新签名不等于 Windows 发布者代码签名。

## 在线验收请求预算（2026-10-04）

- 开发验证先用 Fake/本地测试，单轮最多一次真实 `/releases` metadata Check，不先请求 `/rate_limit`；遇到有效 HTTP 响应后不重复同一 Check。
- 每次正式 Release 最多三次真实 metadata Check：发布前一次、发布后旧客户端一次、新客户端一次。仅明确网络中断且没有有效 HTTP 响应时才允许重试。现有 Feed 的 `per_page=100` 保持。
- 每次真实 API 响应记录 Limit、Remaining、Reset；Remaining=0 时停止非必要 API 测试，结果写 `BLOCKED / RATE_LIMITED`，不写产品 FAIL 或在线 PASS。Remaining<=5 时保留额度给必要的新旧客户端验收，不做额外联网测试。
- 每个最终附件最多匿名下载一次，核对大小/SHA256及已提供的 GitHub digest；通过后复用已有证据，不重复下载来增加测试次数。
- Local/Fake PASS 和在线 PASS 分开报告。公开客户端始终匿名，不嵌入 PAT、OAuth token、cookie 或秘密。限流缓存为独立内部 `update-state.xml`，不改用户 `desktop.xml` schema；普通自动冷却不阻止手动检查，已知限流窗口阻止无效网络请求。
